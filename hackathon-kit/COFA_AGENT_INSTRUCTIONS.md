# COFA 해커톤 에이전트 실행 지침

이 파일을 대회 프로젝트의 AGENTS.md에 필요한 부분만 합치거나, 첫 프롬프트로 읽힌다. 기존 프로젝트 규칙과 대회 안내를 우선한다. 아래 내용은 준비용 실행 지침이며 SK하이닉스의 공식 채점표가 아니다.

## 목표

주어진 시간 안에 사용자의 실제 문제를 해결하는 결과물을 구현한다. 구현이 실행되는지 확인하고, 목표·선택·검증 결과를 간결하게 남기며, 참가자가 자신의 코드와 한계를 설명할 수 있도록 돕는다.

## 시작할 때

1. 제공된 과제, README, 기존 코드, 제출 조건을 먼저 읽는다. 이미 명확한 요구사항을 다시 인터뷰하느라 시간을 쓰지 않는다.
2. 실행 환경·현재 시각·마감·모델/API 사용 범위·데이터 경로를 확인한다. 공개하지 않은 채점 기준·숨은 테스트를 추측해 사실처럼 말하지 않는다.
3. 과제의 실제 사용자, 입력, 원하는 출력, 성공을 판정하는 방법을 짧게 정리한다. 중대한 모호함은 묻고, 되돌릴 수 있는 선택은 가정을 밝히고 진행한다.
4. 새 프로젝트라면 `templates/PROJECT_BRIEF.md`의 항목을 프로젝트 `PROJECT_BRIEF.md`에 채운다. 작은 과제는 한 문단과 검증 표 하나면 충분하다.

## 의도 관리: 사용자의 목표를 유지한다

- 작업을 맡길 때 목적, 입력·출력, 제약, 완료 조건, 확인 방법을 명시한다. 프레임워크 선택보다 요구사항 충족을 우선한다.
- 필수 사용자 흐름을 먼저 끝까지 연결한다. 모델·UI·도구를 계속 늘리기 전에 그 흐름을 실행해 본다.
- 새 기능이 들어오면 원래 성공 조건과 남은 시간을 보고 범위를 조정한다. 변경 이유를 실제 작업 시점에 간단히 남긴다.
- 관련 참고 자료만 검색한다. `CATALOG.md`에서 분야를 찾고, `LOCAL_INDEX.json`에서 실제 경로를 확인한 뒤 README와 필요한 예제만 읽는다. 스킬은 `SKILLS_INDEX.json`을 검색해 필요한 것만 사용한다.
- 막힌 작업은 관찰한 오류 → 원인 가설 → 최소 실험 → 결과 순서로 해결한다. 같은 시도가 계속 실패하면 다른 방법이나 더 작은 구현을 선택한다.
- 세션이 길어지거나 다른 세션에 넘길 때 `HANDOFF.md`에 실행 방법, 현재 상태, 확인된 사실, 실패한 시도, 다음 행동을 남긴다. 실제로 하지 않은 검증을 완료로 표시하지 않는다.

## 기술 관리: 실제 입력에서 작동하게 만든다

- 정상 입력의 핵심 결과를 먼저 구현한다. 이후 빈 입력·잘못된 형식·외부 API 실패 중 과제에 중요한 경우를 검증한다.
- UI 버튼을 실제 처리와 연결한다. 샘플 데이터·stub·미구현 기능은 사용자와 제출 문서에서 알아볼 수 있게 표시한다.
- 중요한 데이터 변환·판정·수치 계산은 검증 가능한 코드로 구현한다. LLM을 쓰는 부분은 구조화 출력 검증과 실패 처리 방법을 둔다.
- API 키는 환경변수로 받고 코드·커밋·로그에 실제 키를 적지 않는다. 외부 API가 필요하면 누락된 환경변수를 명확히 안내한다.
- 의존성 버전과 실행 명령을 해당 프로젝트에 기록한다. 선택한 레포의 README·라이선스·버전에서 사용법을 확인하고 코드 위치와 commit SHA를 출처로 남긴다.
- 테스트는 위험과 요구사항에 맞춘다. 사용자 흐름·계산 정확성·실패 처리를 확인하고, 구현 내용을 그대로 복제하는 테스트를 대량으로 만들지 않는다.
- 마지막 코드 변경 뒤 영향받는 검증을 다시 실행한다. 실패가 있으면 제출 전에 수정하거나 구체적으로 한계를 밝힌다.

## 검증 기록: 주장과 실행을 연결한다

프로젝트 `EVIDENCE.md`에 중요한 실행만 다음 형태로 남긴다. 원본 로그는 필요할 때 `artifacts/`에 저장하고 민감한 입력은 제외한다.

| 요구사항 ID | 실행한 명령/사용자 흐름 | 예상 | 관찰한 결과 | 코드·로그 위치 | 상태 |
| --- | --- | --- | --- | --- | --- |

- 상태는 `PASS`, `FAIL`, `NOT_RUN`으로 구별한다. 실행 시각·데이터 범위·실행 환경이 결과에 영향을 주면 함께 적는다.
- 실패를 고친 경우 관련 수정 뒤 동일한 재현 절차를 다시 수행한다. 처음 성공한 작업을 일부러 망가뜨려 실패 이력을 만들지 않는다.
- “실행됨”, “정확함”, “성능 개선” 같은 문장은 관찰한 범위에서만 쓴다. 실행하지 못했으면 명령과 예상 확인 방법을 남기고 미검증이라고 쓴다.
- 실제 대화·터미널·코드가 근거다. 이 문서만 채워 놓았다고 통과나 득점을 보장하지 않는다.

## 인지 관리: 참가자가 자신의 산출물을 이해하도록 돕는다

큰 변경이 끝날 때 짧게 설명한다.

- 입력이 어떤 파일·함수를 거쳐 결과로 나가는가?
- 중요한 선택은 무엇이고 어떤 대안을 시간·품질·의존성 때문에 제외했는가?
- 지금 실패할 수 있는 구체적인 조건은 무엇이며 사용자에게 어떤 결과가 생기는가?
- 어떤 명령·입력으로 그 위험을 확인할 수 있는가?

`UNDERSTANDING.md`에는 실제 파일·함수 이름을 사용한 데이터 흐름과 가장 중요한 한계만 기록한다. 존재하지 않는 경로·테스트·API를 예시처럼 섞지 않는다. 최종 설명은 제출한 코드와 일치해야 한다.

연습 단계에서는 참가자에게 실제 구현을 묻는 질문을 내고 답변을 구현과 대조할 수 있다. 대회 중 AI 사용이 금지된 확인 문항에는 답을 대신 작성하지 않는다. 사전 설명 자료와 참가자 본인의 이해를 바탕으로 답하게 한다.

## 반도체·제조 데이터 과제에 추가할 조건

- lot·wafer·장비·시간 단위를 먼저 확인한다. 같은 wafer/lot의 관측이 train/test에 섞이는지 검사한다. 시간 예측이면 미래 데이터가 들어가지 않게 분리한다.
- 결측 대치·정규화·특징 선택·재표집은 학습 데이터에서만 적합한다. 평가셋으로 threshold나 하이퍼파라미터를 맞추지 않는다.
- 불량이 드문 문제는 정상만 예측하는 baseline과 비교하고 precision·recall·혼동행렬·알람량을 함께 본다. accuracy 하나로 품질을 판단하지 않는다.
- SHAP·상관관계·예측 특징을 공정 불량의 확정 원인으로 표현하지 않는다. 원인 후보와 추가 확인 계획으로 표시한다.
- 권고와 실제 장비 제어를 구분한다. 시뮬레이션·공개 데이터 결과를 SK하이닉스 현장 성능으로 주장하지 않는다.
- 단위·분모·측정 시점·라벨 지연을 명시한다. 수율, 불량률, recall, 처리량은 서로 다른 지표다.

## 시간과 제출

시간 배분은 실제 제한에 맞춘다. 초기에는 실행 가능한 가장 작은 흐름, 중간에는 핵심 기능과 검증, 끝에는 재실행과 제출 확인에 집중한다. 마감 직전에는 완성도를 해칠 큰 구조 변경보다 필수 실패를 해결한다.

제출 직전에는 `README.md`의 실행 방법으로 다시 시작하고 대표 입력을 처리한다. `PROJECT_BRIEF.md`의 필수 항목과 `EVIDENCE.md`의 결과를 대조한다. 현재 코드 상태·실행 결과·알려진 한계·제출 경로를 정리한다. Git 사용과 제출 방법은 대회 안내에 맞추고 실제 변경이 있을 때 의미 있는 commit을 만든다.
