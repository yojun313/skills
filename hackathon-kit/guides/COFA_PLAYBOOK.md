# COFA 점수 관점의 해커톤 준비 노트

읽는 순서: 이 문서 5분 → `../COFA_AGENT_INSTRUCTIONS.md`를 에이전트에 전달 → 문제 공개 후 실제 조건으로 갱신.

## 먼저 구분할 사실

- **공식 확인:** COFA는 기술·의도·인지의 관점에서 결과물과 작업 과정, 설명을 확인한다. [COFA 소개](https://www.getcofa.com/ko/probe)
- **공식 확인:** SK하이닉스는 Cofa-Probe 등을 이용해 문제 정의·AI 활용·검증을 평가한다고 밝혔다. [SK하이닉스 발표](https://talent.skhynix.com/hub/ko/company/story/237)
- **참가자 경험:** 사용자가 제공한 글은 7월 크래프톤×올리브영의 **다른 대회** 후기다. 글에 나온 축별 100점, FDE의 소통 항목, 확인 문항 수·시간·모델 제한이 SK하이닉스에도 같다고 볼 근거는 없다. [후기](https://brunch.co.kr/@luma/5)
- **일정:** 공식 홈페이지상 10월 31일~11월 1일은 2차 예선, 오프라인 본선은 11월 11일이다. 이 키트는 내일 예선에도 사용할 수 있게 범용으로 작성했다. 개인 안내의 실제 시간·방식이 우선한다. [공식 일정](https://skhynix-hackathon.com/ai-2026)

정확한 배점·통과점·비공개 프롬프트는 확인하지 못했다. 이하의 실행 순서·시간표·문서 형식은 **작성한 준비 전략**이며 공식 가산점 조건이 아니다.

## 당장 기억할 다섯 가지 — 준비 전략

1. 첫 요청에 **누구의 문제 / 입력 / 결과 / 완료 판정**을 적는다.
2. 많은 기능보다 **필수 흐름 하나가 실제로 끝까지 작동**하게 만든다.
3. AI가 완료했다고 말하면 **대표 입력으로 직접 실행**해 확인한다.
4. 중요한 선택의 이유와 검증 결과를 **실제 파일·함수·로그**에 연결한다.
5. 제출 전에는 본인이 **동작·선택 이유·깨지는 조건**을 말로 설명해 본다.

## 평가 관점을 행동으로 바꾸는 표 — 준비 전략

| 관점 | 당일 행동 | 확인할 근거 | 흔한 실패 |
| --- | --- | --- | --- |
| 기술 | 제출 환경에서 처음부터 실행, 핵심 입력 처리 | 실행 명령·응답·대표 결과 | 개발 서버만 켜지고 실제 기능은 비어 있음 |
| 기술 | 중요한 계산과 실패 처리 검증 | 기대값·경계 입력·외부 API 오류 처리 | 수치 계산을 자연어 답변에 맡김 |
| 기술 | 실행과 데이터 처리 책임을 작은 모듈로 나누기 | 실제 파일·함수의 역할 | 리팩터링만 하다가 제출 흐름 미완성 |
| 의도 | 요구사항을 관찰 가능한 완료 조건으로 전환 | 요구사항 ID ↔ 검증 표 | “잘 만들어줘”로 전부 위임 |
| 의도 | 단계마다 결과를 보고 다음 작업 선택 | 실패·원인·수정·재확인 기록 | 모델의 자기 보고만 수용 |
| 의도 | 시간과 새 정보에 맞춰 계획 조정 | 변경 이유·남은 우선순위 | 목표와 무관한 기능 계속 추가 |
| 인지 | 입력부터 결과까지 코드를 따라 설명 | 현재 제출 코드의 경로·함수 | 일반적인 프레임워크 소개만 말함 |
| 인지 | 가장 큰 위험 하나를 구체적으로 설명 | 발생 조건·영향·검증 방법 | “확장성 개선” 같은 추상적 답변 |
| 인계 | 새 세션이 실행할 정보만 요약 | HANDOFF.md·최근 실행 결과 | 채팅 전체를 복사하고 다음 행동 없음 |

## 좋은 첫 프롬프트 — 실제 과제 공개 후 채우기

```text
과제와 README를 먼저 읽고 기존 요구사항을 정리해줘.
사용자는 [누구], 입력은 [실제 데이터/형식], 결과는 [관찰 가능한 산출물]이다.
제한은 [시간/환경/API/데이터], 제출은 [방법]이다.

완료 기준:
R1. [입력 A]를 넣으면 [결과 B]가 나오며 [방법 C]로 확인한다.
R2. [중요한 실패 조건]에서 [기대 동작]을 확인한다.

참고 라이브러리의 AGENTS.md와 COFA_AGENT_INSTRUCTIONS.md를 읽고 적용해줘.
불명확한 큰 조건만 확인하고 작은 선택은 가정을 적고 진행해.
먼저 가장 작은 실행 흐름을 완성하고 실제 입력으로 검증해줘.
중요한 판단·검증·한계는 실제 코드 위치와 함께 짧게 남겨줘.
```

경로는 실제 sandbox의 위치를 쓴다. 홈디렉터리 이름·개발 포트·모델 버전을 미리 가정하지 않는다.

## 시간표 — 제한 시간이 달라도 비율로 적용

| 구간 | 목표 | 다음 단계로 가기 위한 상태 |
| --- | --- | --- |
| 처음 10% | 과제·환경·성공 기준 확인 | 입력·출력·제출 방법이 설명됨 |
| 다음 20% | 가장 작은 사용자 흐름 | 샘플 입력이 실제 결과로 이어짐 |
| 다음 35% | 필수 기능 구현 | 주요 요구사항을 실행으로 확인 |
| 다음 20% | 실패·경계·재실행 확인 | 중요한 실패 수정과 회귀 확인 |
| 마지막 15% | 제출 점검·구현 이해 | 실행 방법·한계·제출물 일치 |

복잡한 환경 설치가 막히면 허용된 기존 스택을 사용한다. 추가 기능을 포기할 기준을 미리 정한다. 별도 확인 문항 시간이 있으면 그 시간을 먼저 제외하고 계산한다.

## 반도체 문제에서 차이가 생길 수 있는 부분 — 준비 전략

- 현업 목표를 지표로 바꾼다. “이상 탐지 정확도”뿐 아니라 작업자가 검토할 알람 수, 놓친 불량, 확인 소요 시간을 본다.
- 공정·설비·시점이 다른 데이터를 한 표로 합칠 때 조인 키와 단위를 확인한다. wafer 이름이 같아도 제품·lot·공장 범위가 다를 수 있다.
- 결측값과 라벨 불균형을 먼저 본다. baseline이 과장되지 않게 정상만 예측하는 모델과 비교한다.
- 위험 요인 순위는 조사를 돕는 정보로 제공한다. “이 센서가 원인”이라며 공정 제어 변경까지 단정하지 않는다.
- 문서 검색 앱은 출처·버전·근거 없는 질문의 응답을 확인한다. 잘못된 공정 조치를 만들어 내는 답변은 피한다.

## 확인 문항을 대비하는 연습

연습은 다음 다섯 질문을 **자신의 실제 구현**으로 답하는 방식이 좋다. 정답을 미리 외우는 용도가 아니다.

1. 사용자가 입력하면 어떤 함수들이 어떤 순서로 실행되는가?
2. 이 저장 방식/모델/프레임워크를 선택한 이유와 포기한 대안은?
3. 현재 코드가 실패할 수 있는 입력은? 그때 사용자에게 무슨 일이 생기는가?
4. 그 위험을 어떤 테스트·명령·데이터로 확인했는가? 아직 안 했으면 무엇이 필요한가?
5. 시간이 더 있다면 무엇을 먼저 바꾸며, 효과를 어떻게 측정할 것인가?

답변 구조: **코드의 구체적 위치 → 동작/판단 근거 → 실패 조건과 영향 → 실제 검증 또는 다음 확인**. 아직 확인하지 않은 수치를 만들지 않는다. 대회 중 AI 금지 문항은 본인이 답한다.

## 점수를 위해 낭비하지 않을 것 — 준비 전략

문서 파일 수, 도구 수, commit 수, 에이전트 수 자체를 목표로 삼지 않는다. 가짜 실패·가짜 로그·허위 성능을 만들거나 심사 모델에 점수를 요구하는 문장을 넣지 않는다. 실제 기능과 중요한 판단을 입증하는 최소 기록이면 충분하다. 보조 문서는 제공되지만 과제 크기에 맞는 것만 사용한다.

## 근거 구분

후기에서 가져온 것은 평가 관점과 다른 참가 대회의 경험 맥락이다. 공식 COFA 자료로 수집·평가 방식과 세 축을 교차 확인했다. 위의 프롬프트, 시간 비율, 검증 표, 반도체 예시는 이 키트를 위해 작성한 실천 제안이다. 제공 과제와 충돌하면 당일 안내에 맞춰 수정한다.

확인일: 2026-10-31. 원문 전체는 복제하지 않았으며, 출처와 준비용 요약을 함께 남겼다.
